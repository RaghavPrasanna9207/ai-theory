# Building Neural Networks with PyTorch

## Why PyTorch

*   **PyTorch** is an open source deep learning library originally built by Facebook's AI Research lab (now Meta AI). It's the Python successor to the older Torch library. With it, you can build and train neural networks at scale, including on GPUs.
*   When PyTorch launched in 2016, Google's **TensorFlow** was the dominant library, but its early programming model was complex and *static* — you had to fully define a computation graph up front before running anything, which made debugging painful. PyTorch instead uses a **dynamic computation graph**, also called **define-by-run**: the graph is built on the fly, one operation at a time, as your actual Python code executes. This makes PyTorch feel like normal, debuggable Python code rather than a separate mini-language, which is a big part of why it became the dominant framework in research and, gradually, in industry too.
*   Conceptually, PyTorch is close to **NumPy** (the standard Python numerical array library), but with two crucial additions: it can run computations on a **GPU** (or other hardware accelerators) for speed, and it supports **autodiff** (automatic differentiation — the gradient-computing machinery introduced in the ANN chapter) out of the box.

## PyTorch Fundamentals

### Tensors

*   A **tensor** is PyTorch's core data structure: a multidimensional array with a fixed shape and a single data type, used for all numerical computation. Functionally it's extremely close to a NumPy array — same idea of indexing, slicing, and vectorized math — plus the GPU/autodiff superpowers mentioned above.
*   You create one much like a NumPy array: `torch.tensor([[1.0, 4.0, 7.0], [2.0, 3.0, 6.0]])` builds a 2×3 tensor. `.shape` and `.dtype` give you its dimensions and data type, and indexing (`X[0, 1]`, `X[:, 1]`) works exactly like NumPy.
*   **A tensor holds exactly one data type** (float, integer, boolean, or complex — never strings). If you mix types when constructing one, PyTorch promotes to the most general type present (complex > float > integer > bool).
*   **Default float precision differs from NumPy**: PyTorch defaults to 32-bit floats, while NumPy defaults to 64-bit. This isn't an oversight — 32-bit halves memory use and speeds up computation, and neural networks essentially never need the extra precision 64-bit floats provide. When converting a NumPy array to a tensor, it's good practice to explicitly request 32-bit (`dtype=torch.float32`), or use the shortcut `torch.FloatTensor(...)` which does this automatically.
*   **Converting between tensors and NumPy arrays**: `.numpy()` converts a tensor to a NumPy array; `torch.tensor(np_array)` converts the other way (and copies the data). `torch.from_numpy()` is an alternative that shares memory with the original NumPy array instead of copying it — convenient, but it means editing one silently edits the other.
*   **In-place operations**: PyTorch's API convention is that any method ending in an underscore modifies the tensor directly instead of returning a new one — e.g., `X.relu_()` applies ReLU and overwrites `X`, whereas `X.relu()` returns a new tensor and leaves `X` untouched. In-place ops can save memory and a bit of time, but (as covered below) they interact awkwardly with autodiff in specific cases, so it's safest to write your model without them first and only introduce them later if you actually need the speedup.

### Hardware acceleration (GPUs and friends)

*   Tensors can live on the CPU or be moved to a GPU (or other accelerator) to speed up computation. PyTorch supports Nvidia GPUs (via CUDA), Apple Silicon (via **Metal Performance Shaders**, MPS), AMD GPUs (via ROCm/DirectML), Intel hardware (via oneAPI), and Google TPUs.
*   A standard device-detection snippet: check `torch.cuda.is_available()` first, then `torch.backends.mps.is_available()`, and fall back to `"cpu"` if neither is present. You then move a tensor to that device with `.to(device)` (or the shortcuts `.cpu()` / `.cuda()`), or create it there directly by passing `device=...` when you construct it.
*   Once a tensor lives on the GPU, every operation on it also runs on the GPU, and the *result* stays on the GPU too — this matters because copying data between CPU and GPU memory is itself slow, so you want to minimize how often you shuttle data back and forth, not just how many operations you run.
*   **How much does a GPU actually help?** It depends heavily on the size of the computation. The book's benchmark: a 1000×1000 matrix multiply took ~16.1ms on CPU vs. ~549µs on a free Colab GPU — a **29× speedup**. But for small matrices (e.g. 100×100), the speedup shrinks to roughly 2×. The reason: GPUs accelerate by splitting one big operation into thousands of small pieces run in parallel across many cores. A small task can't be split into enough pieces to fill all those cores, so the overhead of using the GPU at all starts to dominate — for genuinely tiny operations, plain CPU can even be faster.

### Autograd (PyTorch's autodiff engine)

*   **Autograd** is PyTorch's implementation of **reverse-mode automatic differentiation** (the gradient-computation technique underlying backpropagation, introduced in the ANN chapter). It automatically tracks every operation performed on tensors you've marked as trainable, then computes gradients for you.
*   **Marking a tensor as trainable**: pass `requires_grad=True` when creating it (e.g. `x = torch.tensor(5.0, requires_grad=True)`). PyTorch then silently builds a **computation graph** behind the scenes as you perform operations — every resulting tensor carries a `grad_fn` attribute recording which operation produced it, which is how PyTorch knows how to walk the graph backward later. A tensor you created directly yourself (not the output of some computation) is called a **leaf node** of this graph.
*   **Computing gradients**: call `.backward()` on the final result (e.g., a loss value). This walks the whole computation graph backward from that point, computing the gradient of that value with respect to every leaf tensor that has `requires_grad=True`, and stores each one in that tensor's `.grad` attribute. Example: for $f(x) = x^2$ at $x=5$, `f.backward()` correctly leaves `x.grad` holding `10.0` (the true derivative $f'(x)=2x$ at $x=5$).
*   **A crucial PyTorch-specific quirk: gradients accumulate, they don't get freshly overwritten.** Frameworks like TensorFlow/JAX just hand you the gradient value without side effects; PyTorch instead *adds* newly computed gradients onto whatever is already sitting in `.grad`. This means if you call `.backward()` twice without resetting in between, or if two different loss tensors both depend on the same variable, `.grad` becomes the *sum* of both contributions. Practically, this means you must explicitly zero out gradients (`x.grad.zero_()`, or `optimizer.zero_grad()` when using an optimizer) at the start of every training iteration — if you forget, gradients silently pile up across iterations, corrupting your updates with no explicit error message (just quietly bad training, or eventually `NaN`s), which makes it a nasty bug to track down.
*   **Disabling gradient tracking for actual parameter updates**: after computing gradients, you don't want the *update step itself* (subtracting a fraction of the gradient from the weights) tracked as yet another operation in the graph — and PyTorch will actually raise an error if you try to run certain in-place operations on a tracked leaf tensor. The fix is to wrap the update in a `with torch.no_grad():` block, which tells PyTorch "don't track anything in here." This is also the recommended way to run pure inference (making predictions with an already-trained model) — it uses less memory and runs faster since there's no computation graph to maintain.
*   An alternative to `no_grad()` is `.detach()`, which returns a new tensor that shares the same underlying memory but is disconnected from the computation graph (`requires_grad=False`). It's handy for finer-grained control (e.g., doing some logging computation on a value without it counting toward gradients), but for a plain gradient-descent step or plain inference, `no_grad()` is the more common and convenient choice.
*   **Putting it together, a minimal manual training loop** looks like: forward pass (compute the output/loss) → `loss.backward()` (backward pass) → inside `no_grad()`, subtract `learning_rate * gradient` from each parameter (gradient descent step) → zero out the gradients. Repeating this is, at its core, exactly what "training a neural network" means.
*   **In-place operations can silently break autograd.** Two rules worth internalizing: (1) you can never apply an in-place op directly to a leaf tensor with `requires_grad=True` (PyTorch doesn't know where to record the resulting graph edit); and (2) some operations need to remember either their *input* or their *output* in order to compute gradients correctly during the backward pass, and modifying that remembered value in place before the backward pass runs will corrupt the gradient computation, throwing a `RuntimeError`. Concretely: `exp()`, `relu()`, `sigmoid()`, `tanh()`, and similar functions save their *output* (since, conveniently, the derivative of $e^x$ is $e^x$ itself, so there's no need to remember the original input); functions like `abs()`, `cos()`, `log()`, `sin()` save their *input* instead; a few (`max()`, `min()`, `norm()`) save both; and a few (`ceil()`, `floor()`, `mean()`, `sum()`) save neither and are always safe to modify in place. The practical takeaway: write your first version of any model without in-place ops, and only reach for them later as a targeted memory/speed optimization once you understand which specific operations are safe to touch.

## Implementing Linear Regression

The chapter builds up from raw tensors to PyTorch's high-level API in stages, which is worth following because each stage introduces machinery you'll keep using for every model afterward.

### The low-level way: tensors + autograd directly

*   Load and normalize the California housing dataset (same one used in the ANN chapter), converting NumPy arrays to `float32` tensors and standardizing by subtracting the training mean and dividing by the training standard deviation (computed manually via tensor operations rather than Scikit-Learn's `StandardScaler`, just for practice).
*   **Targets need to be column vectors**, not flat 1D arrays — machine learning code generally prefers a shape like `[m, 1]` (m instances, 1 column) over a bare `[m]`, because it avoids ambiguity in matrix multiplication and broadcasting, and keeps code consistent whether you have one output or several. Use `.reshape(-1, 1)` to add that second dimension (the `-1` tells PyTorch to infer that dimension's size automatically, just like in NumPy).
*   **Creating model parameters manually**: a weight vector `w` (one entry per input feature) initialized *randomly*, and a bias `b` initialized to zero, both with `requires_grad=True`. Random weight initialization matters here for the same reason it mattered for MLPs (breaking symmetry, covered in the ANN chapter) — it's good practice to build the habit even for a model simple enough that it wouldn't strictly matter yet.
*   **The training loop** (batch gradient descent — using the *entire* training set at every step, the simplest and slowest variant): for each epoch, compute predictions (`X_train @ w + b`), compute the mean squared error loss, call `loss.backward()`, then inside a `no_grad()` block subtract `learning_rate * gradient` from both `w` and `b`, then zero out both gradients. This is a direct, literal implementation of everything described in the Autograd section above.
*   **Reproducibility caveat**: `torch.manual_seed()` makes results reproducible on the *same* hardware/software setup, but PyTorch does **not** guarantee bit-identical results across different releases, platforms, or devices — GPU operations in particular get split into parallel chunks whose completion order can vary run to run, introducing tiny floating-point differences that can compound over training into a meaningfully different final model. (There's a `torch.use_deterministic_algorithms(True)` escape hatch, but it trades away speed, and not every operation even supports a deterministic mode.)

### The high-level way: `nn.Linear` and friends

Implementing everything by hand works for linear regression, but would get unmanageable fast for anything bigger. PyTorch's `torch.nn` module (conventionally imported as `nn`) provides building blocks that handle this for you.

*   **`nn.Module`** is the base class for every reusable neural network building block in PyTorch — these building blocks are called **modules**, and you can think of them as interlocking LEGO bricks: small modules combine into bigger ones, all the way up to a full model, which is itself just a module.
*   **`nn.Linear(in_features, out_features)`** implements exactly what a fully connected/dense layer needs: a weight matrix and a bias vector, with `out_features` acting like the number of neurons. Its parameters (`model.weight`, `model.bias`) are randomly initialized automatically, are instances of the special `nn.Parameter` class (a subclass of `Tensor` that PyTorch specifically tracks so it shows up in `model.parameters()`), and are used automatically whenever you call the module like a function — e.g. `model(X_train[:2])` runs a forward pass and returns predictions. Internally, this calls the module's `forward()` method, which for `nn.Linear` computes `X @ weight.T + bias`.
*   You should always call a module like a function (`model(X)`), not call `.forward()` directly — calling it as a function is what lets PyTorch also run any registered **hooks** (custom functions you can attach via `register_forward_hook()` for things like debugging or logging), which get skipped if you bypass the normal call mechanism.
*   **Optimizer and loss/"criterion"**: `torch.optim.SGD(model.parameters(), lr=learning_rate)` creates an optimizer object that knows which parameters to update and by how much; `nn.MSELoss()` creates a **criterion** — PyTorch's term for a loss-function object, used to distinguish the *loss function itself* from the numeric *loss value* it produces on any given batch. Both the optimizer and the criterion are used as simple callables/objects inside the training loop.
*   **A cleaner training loop, using these higher-level pieces**: forward pass (`y_pred = model(X_train)`) → compute the loss via the criterion → `loss.backward()` → `optimizer.step()` (this replaces the manual "subtract learning_rate * gradient" line, and internally does it inside its own `no_grad()`-equivalent, so you don't need to wrap it yourself) → `optimizer.zero_grad()` (replaces manually zeroing each parameter's gradient).
*   A subtlety: `nn.Linear` initializes its weights and bias using a different random distribution than the manual approach above (a specific uniform distribution scaled by the layer size), so even with the same random seed, results from the two approaches won't match exactly — this is fine and expected, just worth knowing so you're not confused when the numbers differ.

## Implementing a Regression MLP

*   **`nn.Sequential`** chains a list of modules end to end: it feeds its input to the first module, feeds that module's output to the second, and so on — since a great many neural networks really are "just a stack of layers," this single class covers most of what you need to define a full MLP in a few lines. Example shape: `nn.Sequential(nn.Linear(n_features, 50), nn.ReLU(), nn.Linear(50, 40), nn.ReLU(), nn.Linear(40, 1))` — two hidden layers (50 then 40 neurons) plus a single-neuron output layer for scalar regression.
*   **`nn.ReLU()`** is the activation function as its own module — it holds no parameters, and its output shape always matches its input shape (it's applied elementwise).
*   **Shape rules to internalize, since they'll trip you up constantly at first**: the *first* layer's input size must match your actual feature count; every layer's output size is a free hyperparameter you choose; but every subsequent layer's input size must exactly match the *previous* layer's output size; and the *final* layer's output size is fixed by the problem (1 for scalar regression, matching earlier guidance from the ANN chapter). Shape mismatches are one of the most common early PyTorch errors, so it's worth deliberately breaking a model (e.g. by mismatching two adjacent layer sizes) once just to see what the resulting error message looks like.
*   Training an MLP built this way uses the exact same training-loop pattern as linear regression above — nothing changes except the model itself is deeper.

## Mini-Batch Gradient Descent with DataLoaders

Training on the *entire* dataset at every step (batch gradient descent) doesn't scale to large datasets. PyTorch's tools for mini-batch training:

*   **`TensorDataset`** wraps a set of tensors (e.g. `X_train`, `y_train`) into an object that knows how many samples it has (`__len__`) and how to fetch one by index (`__getitem__`) — the two methods any PyTorch dataset needs to implement.
*   **`DataLoader`** wraps a dataset and handles pulling out batches of a given `batch_size`, optionally shuffling the data at the start of every epoch (`shuffle=True`, which you want for training but not for validation/test evaluation).
*   **Moving the model (and data) to the GPU**: `model = model.to(device)` moves every parameter to GPU memory; then, inside the training loop, each individual batch pulled from the `DataLoader` must *also* be moved to the same device before being fed to the model (`X_batch.to(device)`, `y_batch.to(device)`), since a computation can't mix tensors that live on different devices. **Create the optimizer only after moving the model to the GPU** — some optimizers keep their own internal state tensors (covered further in the Training Deep Neural Networks chapter), and that state gets allocated on whatever device the parameters were on *at the time the optimizer was created*.
*   **`model.train()` vs. `model.eval()`**: these switch the model (and all its submodules) between *training mode* and *evaluation mode*. For a plain MLP this makes no visible difference yet, but certain layers (dropout, batch normalization — both covered in the next chapter) genuinely behave differently depending on the mode, so it's a habit worth building now: call `model.train()` before a training loop, `model.eval()` before evaluating or making predictions.
*   **PyTorch deliberately does not ship a built-in training loop** — you write your own `for` loop over epochs and batches. This is a real design choice (favoring flexibility and transparency over convenience), though libraries like PyTorch Lightning, FastAI, or Keras (which now supports PyTorch as a backend) exist if you'd rather not write the loop yourself.
*   **Two practical speed tweaks once you're using a GPU**: setting `pin_memory=True` on the `DataLoader` allocates the CPU-side batch data in a special fixed ("page-locked") memory region that supports faster direct transfer to the GPU, skipping an intermediate copy; and setting `num_workers` to a positive number spins up background processes that prepare the *next* batch(es) on the CPU while the GPU is still busy with the current one, avoiding idle GPU time between batches. Both are tuning knobs whose ideal value depends on your specific hardware.

## Model Evaluation

*   A simple pattern: write an `evaluate()` function that switches to `model.eval()`, disables gradient tracking (`with torch.no_grad()`), loops through a validation/test `DataLoader` computing some metric per batch, and finally aggregates all the batch-level results (by default, averaging them).
*   **A subtle trap worth understanding, not just memorizing**: averaging a metric computed separately on each batch is *not* always the same as computing that metric over the whole dataset at once. RMSE is the textbook example — the square root doesn't distribute over averaging, so "average of per-batch RMSEs" ≠ "RMSE of the whole set." The fix: aggregate the raw per-batch MSE values first (averaging *does* distribute correctly over MSE, since MSE is already a mean), and only take the square root at the very end, after aggregation.
*   Rather than hand-rolling metrics and worrying about traps like the one above, the **TorchMetrics** library (from the same team as PyTorch Lightning) provides pre-built **streaming metrics** — objects that accumulate correctly across many batches (`metric.update(y_pred, y_batch)` per batch, `metric.compute()` once at the end) and get this kind of aggregation right automatically. `torchmetrics.MeanSquaredError(squared=False)` gives you a correctly-computed streaming RMSE, for example.
*   As in earlier chapters, if training-set performance is much better than validation-set performance, that's the standard overfitting signal (or, alternatively, a data mismatch bug) — and plotting the learning curves (training vs. validation metric over epochs, as introduced in the Training Models chapter) remains the best way to actually diagnose it.

## Building Nonsequential Models Using Custom Modules

Not every useful architecture is a straight stack of layers. A concrete motivating example from the chapter is the **Wide & Deep** architecture (Cheng et al., 2016): it feeds the raw inputs *directly* into the output layer, in parallel with a normal stack of hidden layers (the "deep" path), then concatenates both paths right before the final prediction. The intuition: forcing every input through several transformation layers (as a plain MLP does) can distort simple, already-useful patterns in the raw data; giving the network a "short path" alongside the "deep path" lets it learn both simple linear rules *and* complex nonlinear ones, without one having to fight through the other's transformations.

*   **Building any custom architecture**: subclass `nn.Module`, define whatever sub-layers you need inside `__init__()` (after calling `super().__init__()`), and define exactly how data flows through them in a `forward()` method you write yourself. This is the general escape hatch for anything `nn.Sequential` can't express — branches, merges, skip connections, whatever the architecture calls for.
*   For the Wide & Deep example: the constructor builds a `deep_stack` (an `nn.Sequential` of hidden layers) and a separate output layer sized to accept the *concatenation* of the raw input and the deep stack's output. The `forward()` method runs the input through the deep stack, concatenates the raw input alongside the deep stack's output (`torch.concat([X, deep_output], dim=1)`), then feeds that combined tensor to the output layer.
*   If a model needs a *variable* number of submodules (rather than a fixed handful you name individually), store them in an `nn.ModuleList` (or `nn.ParameterList` for a variable number of raw parameters) rather than a plain Python list — only these PyTorch-aware containers get properly picked up by `.parameters()`, `.children()`, and friends.

### Models with multiple inputs

Some architectures need inputs that can't naturally live in one combined tensor — e.g. different subsets of features routed to different paths (wide vs. deep), or genuinely different data types like images and text side by side.

*   The cleanest approach: give `forward()` multiple named arguments (e.g. `forward(self, X_wide, X_deep)`), and build a `TensorDataset`/custom `Dataset` that returns multiple input tensors per sample instead of one.
*   When calling the model in your training loop, you can either accept the multiple returned tensors positionally and pass them in order, or — safer once a model has several inputs, since it's easy to accidentally swap the order — write a custom `Dataset` that returns a *dictionary* of named inputs, and call the model with `model(**inputs)`, unpacking by name rather than position. The trade-off is explicitness versus a bit more boilerplate; the dictionary approach is worth it once a mixed-up argument order becomes a realistic risk.

### Models with multiple outputs

Reasons you might want more than one output neuron *group* (not just more than one class, but genuinely separate output heads):

*   **The task itself has multiple parts** — e.g. simultaneously locating an object (regression: coordinates) and classifying it (classification: category).
*   **Multiple genuinely independent labels sharing the same input** — e.g. classifying a face's expression *and* separately detecting whether they're wearing glasses. Training one network with two output heads instead of two separate networks often works *better* for both tasks, because the shared lower layers learn features useful to both simultaneously (this is a form of **multitask learning**).
*   **Regularization via an auxiliary output.** You can attach an extra "auxiliary" output partway through the network (e.g., directly off the deep stack, before it merges with the wide path) purely as a training aid — it forces that earlier part of the network to be independently good at the task on its own, rather than only being useful in combination with the rest. This auxiliary output isn't used at prediction time; its only job is to shape training.
*   **Mechanically**: `forward()` returns a tuple of outputs (main and auxiliary). The training loop computes a separate loss for each output, then combines them into one scalar loss as a **weighted sum** (e.g. `loss = 0.8 * main_loss + 0.2 * aux_loss`) — the weighting ratio is itself a regularization hyperparameter you can tune, favoring the main output since that's what you actually care about at inference time. During evaluation, you typically just discard the auxiliary output and score the model only on the main one.

## Building an Image Classifier with PyTorch

This section repeats the Fashion MNIST classification task from the ANN chapter, but now with PyTorch and its computer-vision companion library.

*   **TorchVision** is PyTorch's computer vision toolkit: dataset downloaders for common benchmarks (MNIST, Fashion MNIST, etc.), pretrained models, and image transform utilities. `torchvision.datasets.FashionMNIST(root=..., train=True/False, download=True, transform=...)` downloads and wraps the dataset directly as a PyTorch-compatible `Dataset`.
*   **Transforms**: images load by default as raw PIL (Python Image Library) images with integer pixel values 0–255. A `transform` (composed via `T.Compose([...])`, chaining a `ToImage` step and a `ToDtype(torch.float32, scale=True)` step) converts them to properly scaled 32-bit float tensors on the fly, each time a sample is accessed.
*   **Image tensor shape convention**: PyTorch represents an image as `[channels, height, width]` — channels *first*. This is the opposite convention from many other libraries (Matplotlib, PIL, TensorFlow, OpenCV), so this is a very common source of "why does my image look scrambled/why did this crash" bugs when moving data between libraries; `torch.permute()` reorders dimensions if you ever need to convert between conventions. A grayscale image like Fashion MNIST has 1 channel; color images typically have 3 (covered in the CNN chapter).
*   **`nn.Flatten()`** is the layer that converts a batch of `[batch, 1, 28, 28]` image tensors into `[batch, 784]`, which is what a `nn.Linear` layer expects as input (dense layers only understand flat feature vectors, not 2D grids) — it holds no parameters, it's a pure reshape.
*   **`nn.CrossEntropyLoss`, and a subtlety about logits vs. probabilities**: the ANN chapter said multiclass classification wants a softmax activation on the output layer. In PyTorch practice, though, `nn.CrossEntropyLoss` is built to compute cross-entropy directly from raw, unnormalized **logits** (the pre-softmax class scores from the Training Models chapter) rather than from probabilities — internally fusing the softmax and cross-entropy math in a way that's faster and more numerically stable (avoiding computing logarithms and exponentials that would otherwise partially cancel out anyway). The practical consequence: **your model's output layer should have no activation function at all** when paired with `nn.CrossEntropyLoss`, and if you actually want probabilities (e.g. for display, or `predict_proba`-style output), you compute them yourself afterward by calling `F.softmax(logits, dim=1)` (`F` being the conventional alias for `torch.nn.functional`, a module of stateless functional versions of many `nn` operations).
*   **Alternative loss formulations** (situational, not needed by default): pairing `nn.LogSoftmax` on the output layer with `nn.NLLLoss` (negative log-likelihood loss) achieves the same underlying math but has the model output log-probabilities instead of raw logits — slightly slower, but occasionally useful if you specifically want log-probabilities as your model's actual output. For **binary** classification, use one output neuron with `nn.BCEWithLogitsLoss` (binary cross-entropy from logits — analogous reasoning to `CrossEntropyLoss` above), or, if you'd rather the model output probabilities directly, add `nn.Sigmoid` to the output layer and pair it with plain `nn.BCELoss` (again, a bit slower/less numerically stable). Multilabel binary classification just needs one output neuron per label, using the same binary-loss machinery per label.
*   **Getting probabilities and top-k predictions after the fact**: `F.softmax(logits, dim=1)` for full probabilities; `torch.topk(logits, k=4, dim=1)` returns both the top-k logit values and their class indices in one call, handy for "show me the model's top few guesses and their confidence" style output.
*   **Class imbalance**: if some classes are far rarer than others in your training data, `nn.CrossEntropyLoss` accepts a `weight` argument — a tensor giving each class a multiplier on its contribution to the loss, so rare classes aren't drowned out. (Fashion MNIST itself is perfectly balanced, so this doesn't come up in the worked example, but it's a common real-world necessity.)
*   **Label smoothing** (introduced conceptually in the ANN chapter, as a fix for models being overconfident) is available as a simple built-in: pass `label_smoothing=0.05` (or similar) directly to `nn.CrossEntropyLoss`.
*   **Chapter's actual result**: with two hidden layers (300 and 100 neurons) and plain SGD, the model reached roughly **92.8% training accuracy** and **87.2% validation accuracy** — a visible gap indicating a bit of overfitting, consistent with the ANN chapter's observation that neural nets with lots of parameters are prone to it; the suggested next step is exactly what the next chapter (Training Deep Neural Networks) focuses on — regularization techniques to close that gap.

## Fine-Tuning Neural Network Hyperparameters with Optuna

Manually guessing good hyperparameters (as covered in the ANN chapter's tuning guidelines) only gets you so far. **Optuna** is a dedicated hyperparameter search library (alternatives: Ray Tune, Hyperopt) that automates the search more intelligently than plain grid/random search.

*   **The core pattern**: write an `objective(trial)` function that (a) asks the `trial` object for candidate hyperparameter values — `trial.suggest_float("learning_rate", 1e-5, 1e-1, log=True)`, `trial.suggest_int("n_hidden", 20, 300)`, etc. — (b) builds and trains a model using those values, and (c) returns a single score (typically validation accuracy or similar) that Optuna is trying to optimize.
*   **`log=True` on a float suggestion matters**: for a hyperparameter like learning rate, where good values could plausibly be anywhere from $10^{-5}$ to $10^{-1}$, sampling *uniformly* across that range would almost never land on the tiny end (since the vast majority of the numeric range is dominated by larger values) — sampling on a *log* scale instead makes the search explore all orders of magnitude roughly equally.
*   **Running the search**: create a `Study` (`optuna.create_study(direction="maximize", sampler=...)` — `direction="maximize"` since higher validation accuracy is better; Optuna minimizes by default) and call `study.optimize(objective, n_trials=N)`. By default, Optuna uses the **Tree-structured Parzen Estimator (TPE)** algorithm — a *sequential model-based* search, meaning each new trial's hyperparameters are chosen based on what's been learned from *previous* trials' results, progressively focusing the search on the most promising regions of the hyperparameter space rather than sampling blindly. This is why it typically beats plain random search given the same time budget.
*   **Reading results**: `study.best_params` and `study.best_value` give you the winning hyperparameter combination and the score it achieved.
*   **Pruning bad trials early** saves a lot of wasted compute: if a trial's loss is clearly diverging or barely improving after a few epochs, there's no point letting it run to completion. Optuna's `MedianPruner` (or other `Pruner` classes) automatically compares a trial's in-progress performance against the median of past trials' performance at the same epoch, and lets you bail out early — inside the training loop, call `trial.report(current_score, epoch)` after each epoch, then `raise optuna.TrialPruned()` if `trial.should_prune()` returns true.
*   **Practical caution**: every extra hyperparameter you add to the search space multiplies the size of that space, so search time grows fast — only add a hyperparameter to the automated search if the potential gain is worth the extra compute.

## Saving and Loading PyTorch Models

*   **The simplest approach** — `torch.save(model, "model.pt")` and `torch.load("model.pt", weights_only=False)` — serializes the *entire* model object using Python's `pickle` module. It's convenient, but has two real drawbacks worth taking seriously: **pickle is a security risk**, since the format can embed arbitrary executable code that runs automatically the moment the file is loaded — never load a pickled model from a source you don't fully trust; and pickle is **brittle across environments**, since it references exact file paths and can behave differently across Python versions.
*   **The recommended approach**: save only the model's *weights* via its **state dictionary** — `torch.save(model.state_dict(), "weights.pt")`. A state dict is just an ordered mapping from parameter name to tensor value (plus any registered **buffers** — non-parameter tensors a model needs to keep around, such as running statistics used by batch normalization in the next chapter). This file contains *only data*, no executable code, so it's both safer and more portable. The catch: to load it back, you must first reconstruct a model with the *exact same architecture* (layer sizes, etc.) before calling `new_model.load_state_dict(loaded_weights)` — so it's good practice to also save the hyperparameters needed to reconstruct that architecture (e.g. in a small dictionary alongside the state dict) rather than hardcoding them separately somewhere you might forget to update.
*   The **safetensors** library (from Hugging Face) is another increasingly popular option specifically designed to store weights safely without pickle's risks.

## Compiling and Optimizing a PyTorch Model

*   **TorchScript** is a statically-typed subset of Python that PyTorch can convert your model into, for two reasons: it enables compiler-level optimizations (fusing multiple operations into one, folding constant expressions, pruning dead code) for faster inference, and it can be saved and run outside Python entirely (via the C++ **LibTorch** library), which matters for deploying to environments where a full Python runtime isn't practical (e.g. embedded devices).
*   Two ways to produce TorchScript: **tracing** (`torch.jit.trace()`) runs your model once on sample data and records the exact sequence of operations that happened — this works great for straightforward models, but silently "bakes in" whatever branch of an `if` or however many loop iterations happened to execute during that one trace run, which is usually *not* what you want for a model whose control flow can vary. **Scripting** (`torch.jit.script()`) instead directly parses your actual Python source code, so it correctly preserves real conditionals and loops — at the cost of only supporting a restricted subset of Python (no global variables, no generators, fixed return types, and so on).
*   **`torch.compile()`** is the newer, generally-preferred optimization path (PyTorch 2.0+): wrap your model with `torch.compile(model)` and use it completely normally — the compilation and optimization happen automatically and transparently the first time it's actually run (**Just-In-Time**, or JIT, compilation, as opposed to compiling everything up front / Ahead-Of-Time). Under the hood this relies on components named TorchDynamo (captures the computation graph directly from Python bytecode, correctly handling conditionals/loops without tracing's pitfalls) and TorchInductor (generates optimized GPU or CPU code from that graph).

## Questions and Answers

### 1. PyTorch is similar to NumPy in many ways — what extra features does it offer?

The two big ones: **automatic differentiation** (autograd — the ability to automatically compute gradients of any computation with respect to tensors marked `requires_grad=True`), and **hardware acceleration** (tensors can live on and compute on a GPU or other accelerator, not just the CPU). PyTorch also ships with ready-to-use optimizers and neural network building blocks (the `nn` module), which NumPy has no equivalent of.

### 2. What's the difference between `torch.exp()` and `torch.exp_()`, or `torch.relu()` and `torch.relu_()`?

The underscore suffix marks an **in-place** operation. `torch.exp(x)` (or `x.exp()`) returns a *new* tensor holding the result, leaving `x` unchanged. `torch.exp_(x)` (or `x.exp_()`) instead overwrites `x` directly with the result. Same relationship for `relu()`/`relu_()`, and this underscore convention holds across essentially the whole PyTorch API.

### 3. What are two ways to create a new tensor on the GPU?

(1) Pass `device="cuda"` (or `"mps"`, etc.) directly to the tensor-creation call, e.g. `torch.randn(10, device="cuda")` — this creates it on the GPU immediately, which is the more efficient option. (2) Create it normally on the CPU, then move it with `.to("cuda")` (or the `.cuda()` shortcut) — this works but involves an extra CPU→GPU copy that direct creation avoids. (A third option worth knowing: the `*_like()` family, e.g. `torch.zeros_like(existing_tensor)`, creates a new tensor on the same device — and with the same dtype — as an existing one.)

### 4. What are three ways to perform tensor computations without using autograd?

(1) Simply use tensors created with `requires_grad=False` (the default — autograd only tracks tensors you've explicitly opted in). (2) Run the computation inside a `with torch.no_grad():` block, which suspends tracking for everything inside it regardless of the tensors' individual settings. (3) Call `.detach()` on a tensor to get a version of it that's disconnected from the computation graph before doing further computation with it.

### 5. Will `z = t.cos().exp_(); z.backward()` cause a `RuntimeError`, given `t = torch.tensor(2.0, requires_grad=True)`? What about swapping the order?

No error in the original version: `t.cos()` creates a new (non-leaf) intermediate tensor, and `exp_()` then modifies *that* intermediate tensor in place — which is fine, since `exp()`'s backward pass only needs its own *output* (not `t.cos()`'s original value) to compute gradients, and that output is exactly what got preserved. Swap it to `z = t.cos_().exp()`, however, and you get an immediate `RuntimeError`, because now the in-place op (`cos_()`) is being applied directly to `t` itself — and `t` is a leaf tensor with `requires_grad=True`, which can never be modified in place (PyTorch has nowhere to record that edit against the original leaf). Swap it to `z = t.exp().cos_()` instead: this also errors, but for a different reason — `cos()`'s backward pass needs to remember its *input* (not its output) to compute the gradient, and `cos_()` immediately overwrites that very input in place before the backward pass ever gets to use it.

### 6. What does a `Linear(100, 200)` module look like — neurons, parameter shapes, input/output shape?

It represents a layer of 200 neurons, each fully connected to 100 inputs. Its `weight` parameter has shape `[200, 100]` (PyTorch stores one row per neuron/output, one column per input feature — the transpose of the convention used in the linear-algebra layer equation from the ANN chapter), and its `bias` parameter has shape `[200]` (one bias per neuron). It expects an input tensor of shape `[batch_size, 100]` and produces an output of shape `[batch_size, 200]`.

### 7. What are the main steps of a PyTorch training loop?

Pull a batch of samples (typically via a `DataLoader`) → move the batch to the target device if using a GPU → run it through the model to get predictions (`y_pred = model(X_batch)`) → compute the loss via the criterion → backpropagate (`loss.backward()`) → take an optimizer step (`optimizer.step()`) → zero out the gradients (`optimizer.zero_grad()`) → repeat for every batch, typically organized into epochs (one full pass over the training set per epoch).

### 8. Why create the optimizer *after* moving the model to the GPU?

Many optimizers (covered further in the Training Deep Neural Networks chapter) maintain their own internal state tensors alongside the model's parameters (e.g. running averages used for momentum-style updates). That state gets allocated on whichever device the model's parameters live on *at the moment the optimizer is constructed* — so if you create the optimizer first and move the model afterward, the optimizer's internal state ends up stranded on the wrong device, causing device-mismatch errors or silently broken training.

### 9. What `DataLoader` options generally speed up GPU training?

`num_workers` (spawns background processes to prepare upcoming batches on the CPU while the GPU processes the current one, avoiding idle GPU time), `pin_memory=True` (allocates batch data in page-locked CPU memory for faster transfer to the GPU), and — if worker startup overhead is itself a bottleneck, which can happen especially on Windows — `persistent_workers=True` to reuse the same worker processes across epochs instead of respawning them every epoch.

### 10. What are the main PyTorch classification losses, and when should each be used?

`nn.CrossEntropyLoss` — the standard choice for multiclass classification; it's efficient and numerically stable specifically because it operates on raw logits rather than probabilities, so your model's output layer must *not* include a softmax (you apply `F.softmax()` yourself afterward only if you need actual probabilities). `nn.NLLLoss`, paired with an `nn.LogSoftmax` output layer, achieves equivalent results but has the model output log-probabilities directly instead of logits — a bit slower, useful mainly when you specifically want that log-probability output. `nn.BCEWithLogitsLoss` — for binary (or multilabel binary) classification, again operating on logits for efficiency/stability, requiring one output neuron per label with no activation function. `nn.BCELoss` — the probability-based alternative to `BCEWithLogitsLoss`, used when the output layer includes a sigmoid and the model outputs probabilities directly; slower and less numerically stable, but convenient when you want direct probability outputs.

### 11. Why call `model.train()` before training and `model.eval()` before evaluation?

Some layer types — dropout and batch normalization being the prime examples, both covered in the next chapter — genuinely *behave differently* depending on whether the model is in training or evaluation mode (e.g. dropout randomly disables neurons during training but must not do so during evaluation). Calling the right mode-switch method ensures every submodule in the model is behaving correctly for the situation; forgetting it produces predictions that are silently wrong or inconsistent, without necessarily throwing an error.

### 12. What's the difference between `torch.jit.trace()` and `torch.jit.script()`?

Both convert a PyTorch model into TorchScript for optimization/deployment, but by different mechanisms. **Tracing** runs the model once with sample input and records the literal sequence of operations that executed — simple and broadly compatible, but it silently locks in whatever specific branch of any `if` statement happened to run, and unrolls loops into a fixed number of repeated operations based on how many iterations happened to occur during that one trace — both wrong for a model whose control flow can vary between calls. **Scripting** instead parses your actual Python source code and converts it directly, correctly preserving real conditionals and loops as genuine conditionals and loops in the resulting TorchScript — at the cost of only supporting a restricted, statically-typeable subset of Python (no global variables, no generators, no variable-length `*args`/`**kwargs`, fixed return types, and so on).

### 13. Use autograd to find the gradient of $f(x,y) = \sin(x^2 y)$ at $(x,y) = (1.2, 3.4)$.

Create `x` and `y` as scalar tensors with `requires_grad=True`, compute `result = torch.sin(x**2 * y)`, call `result.backward()`, and read off `x.grad` and `y.grad`. This gives $\frac{\partial f}{\partial x} \approx 1.4899$ and $\frac{\partial f}{\partial y} \approx 0.2629$ — matching the analytical derivatives $\frac{\partial f}{\partial x} = 2xy\cos(x^2y)$ and $\frac{\partial f}{\partial y} = x^2\cos(x^2y)$ evaluated at that point, and matching a manual finite-difference approximation (nudging $x$ and $y$ by a tiny $\varepsilon$ and measuring the resulting change in $f$) to several decimal places.

### 14. Build a custom `Dense` module equivalent to `nn.Linear` + `nn.ReLU`.

The straightforward version simply composes the two existing modules inside a custom `nn.Module`: store an `nn.Linear` and an `nn.ReLU` as sub-modules in `__init__`, and have `forward()` apply the linear layer followed by the ReLU. A more "from scratch" version skips `nn.Linear` entirely: store the weight and bias directly as raw `nn.Parameter` tensors (`nn.Parameter(torch.randn(out_features, in_features))` for the weight, `nn.Parameter(torch.zeros(out_features))` for the bias), and have `forward()` compute `F.relu(X @ weight.T + bias)` by hand — functionally identical, just built from lower-level pieces. A refinement worth knowing (previewed here, developed fully in the next chapter): when the activation function is ReLU, it's better to initialize the weights using **Kaiming initialization** (`nn.init.kaiming_uniform_(weight, nonlinearity="relu")`) rather than plain random normal values, since it's specifically calibrated to keep signal variance stable through ReLU layers.

### 15. Build and train a classification MLP on the CoverType dataset — can you reach 93% test accuracy?

Yes. Loading the data via `sklearn.datasets.fetch_covtype()`, standardizing the 54 numeric features, and shifting the target labels down by 1 (since they arrive numbered 1–7 but `nn.CrossEntropyLoss` expects class indices starting at 0) sets up the data. Wrapping it in a `TensorDataset` plus `random_split()` (80% train / 10% validation / 10% test) and `DataLoader`s (batch size 256) handles batching. A 3-hidden-layer MLP (200 → 100 → 50 neurons, ReLU activations, no activation on the 7-neuron output layer since `nn.CrossEntropyLoss` expects raw logits) trained with plain SGD, using a manually annealed learning rate schedule — starting at 0.16 and stepping down through 0.08, 0.04, 0.02, 0.01, to 0.005 (15 epochs at each rate, ~90 epochs total) — reached **94.88% accuracy on the held-out test set**, comfortably clearing the 93% target. The stepped-down learning rate schedule is doing real work here: it lets training move quickly early on with a large learning rate, then take smaller, more precise steps later as it gets close to a good solution — the same "reduce the learning rate as training progresses" idea behind the *learning schedules* covered for plain gradient descent back in the Training Models chapter, just applied manually here rather than through a built-in scheduler.
